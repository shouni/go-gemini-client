# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Go library wrapping the official `google.golang.org/genai` SDK for Gemini API / Vertex AI, plus generation workflows built on top of it. Five packages plus one internal, no main:

- `gemini/` — retrying client (text/multimodal generation, File API upload with Active-state polling, response extraction into `Response{Text, Images, Audios, Attachments}`, and the one-round-trip Veo video surface `StartVideo`/`PollVideo`)
- `music/` — the shared song-structure vocabulary (`music.Recipe`/`Section`/`LyricsDraft`/`AIModels`). A dependency-free leaf so downstream repos that only need the types don't import the whole workflow; `lyria` re-exports them under the old names (`lyria.MusicRecipe = music.Recipe`)
- `lyria/` — lyrics → recipe → audio music generation using `gemini.Generator`, exposed as three independently callable steps
- `veo/` — Veo video generation: submits the long-running operation and owns *how to wait* for it, using an injected `gemini.VideoGenerator`
- `callguard/` — rate interval + per-execution timeout + singleflight dedup for expensive AI calls. A leaf that imports only `x/sync` and `x/time`; `lyria` uses it, and downstream kits (`go-comic-kit`, `go-veo-orchestrator`) consume it instead of keeping their own copies
- `internal/poll` — the polling skeleton both long waits share (`gemini.waitForFileActive`, `veo.Client.Wait`): fire the first attempt with no interval wait, then one attempt per interval, with the deadline covering the in-flight attempt and a tolerance for consecutive transient failures. **The deadline has to cover the attempt itself**: genai's default HTTP client is `&http.Client{}` with no timeout of its own, so a call that never answers never yields to a timeout branch that only runs between attempts — which is exactly the bug the File API wait carried while the two loops were written out separately. It stays `internal` because its shape is these two callers' needs; a public "generic polling" API would grow retry and backoff knobs neither one wants

**This module is the only place in the workspace that imports `google.golang.org/genai`.** Downstream repos depend on it precisely so the SDK stays confined here; adding a direct genai call anywhere else defeats that. When a Google AI API is not yet wrapped, add it here rather than hand-rolling REST in the app.

## Commands

```sh
go build ./...
go vet ./...
go test -race ./...                          # CI runs tests with -race
go test ./gemini/ -run TestShouldRetry       # single test
test -z "$(gofmt -l .)"                      # CI fails on unformatted code
golangci-lint run                            # CI uses v2.12.2; config in .golangci.yml
```

Tests requiring GCP Application Default Credentials (Vertex AI client construction) skip themselves automatically via `skipWithoutGCPCredentials`.

## Architecture

### gemini package

- `Client` wraps the genai SDK behind three small internal interfaces (`modelClient`, `fileClient`, `videoClient` in `sdk.go`); tests substitute fakes (`fakeModelClient`, `fakeFileClient`, `fakeVideoClient`) instead of hitting the network.
- **Retry**: retries belong to the **genai SDK**, not to this package. `Config.retryOptions()` maps `MaxRetries` / `InitialDelay` / `MaxDelay` onto `genai.HTTPRetryOptions`, `toClientConfig` attaches it to `ClientConfig.HTTPOptions`, and `DisableRetry` returns nil — which the SDK reads as a single attempt. Do not re-copy the SDK's status table (408/429/5xx plus transport failures) into this package; that duplication is what the migration removed. Two traps: polling opts out per request via `noRetryHTTPOptions()`, and **the File API upload is the one path the SDK does not retry** (see File API below). `Jitter` is set to half the initial delay because the SDK default only adds U(0, 1s).
- **Config**: `APIKey` (Gemini API) and `ProjectID`+`LocationID` (Vertex AI) are mutually exclusive; validation and backend selection live in `config.go`. Defaults (retry, file polling) are resolved once in `NewClient` — Client fields are always populated, no fallback at use sites.
- **File API**: `UploadFile` returns an `UploadedFile{URI, Name}` struct — the two are both strings with different uses (`URI` goes into `genai.FileData`, `Name` into `DeleteFile`), so they are not returned as bare strings. It polls until the file is Active; on failure after a successful upload it fires `asyncDelete` (detached via `context.WithoutCancel` so trace values survive, bounded by `Config.AsyncCleanupTimeout`, fire-and-forget — there is no way to await it). Upload streams the reader straight through and is **not** retried (genai withholds retry options from the resumable upload loop); Delete treats 404 as success (the goal is absence) and does get the SDK's retries. The Active-state *poll* deliberately does not retry per call — it passes `noRetryHTTPOptions()` to opt out of the client's retries — and `waitForFileActive` absorbs up to `fileStateMaxPollErrors` consecutive transient failures instead (same philosophy as `veo.Client`). **How to wait is `internal/poll`'s**, so `waitForFileActive` supplies only what to poll, what to call the subject in an error, and how to log a transient failure; `FilePollingTimeout` bounds the whole wait including the status check in flight. `TestWaitForFileActive_TimeoutBoundsInFlightCheck` pins that — against a loop that only checks the deadline between polls it deadlocks the synctest bubble rather than failing an assertion.
- Public consumer-facing interfaces are in `interfaces.go` — exactly five (`Generator`, `BackendInspector`, `FileManager`, `Model`, `VideoGenerator`), none of which mention genai types. `lyria` and downstream apps mock against these. Streaming, token counting, and the genai-typed `GenerateWithParts`/`GenerateContentStream` family were deleted in v1.17 after a survey showed zero consumers across all ten downstream repos; git history has them if ever needed again.
- **All public generation entry points are genai-free.** `GenerateWithAttachments` takes a prompt plus `[]Attachment` (`MIMEType` + either `Data` or `URI`) and builds parts internally via the unexported `generateParts`; `GenerateContent` is the no-options text shortcut kept because ap-comp calls it. `attachmentParts` in `attachment.go` is the one place that converts; it drops empty attachments (callers assemble optional images as "pass it if we have it"), rejects `Data`+`URI` together, and requires a MIME type only for inline data since a URI's type can be left to the server.
- **`Attachment.validateSource` is the single definition of "Data and URI are exclusive".** It takes the sentinel to wrap because the same misuse classifies differently by path — `ErrInvalidAttachment` for generation input, `ErrInvalidVideoInput` for video input — and downstream `errors.Is` checks depend on that split.
- **`Response.Attachments` exists so callers can know the MIME type of returned media.** `Images`/`Audios` are bytes only, so deciding a file extension or Content-Type used to mean walking the raw genai response. `Attachments` carries the MIME type alongside the bytes, in return order. (`Response.RawResponse` was removed — nothing read it.)
- **`Schema`/`SchemaType` are aliases of the genai types too**, with `TypeObject`/`TypeString`/… re-exported. Structured output was the last thing that forced downstream repos to import genai directly (four hand-written schema files across three repos did), and an alias closes it at zero maintenance cost — it is the same type, so existing `*genai.Schema` values still pass. `lyria/schemas.go` uses the aliases, which is why the `lyria` package no longer references genai at all.
- **`SafetyThreshold` and `ThinkingLevel` are aliases of the genai types**, with `SafetyBlockNone`/`ThinkingMinimal`/… constants re-exported. This keeps `NewSafetySettings`'s signature unchanged while letting callers pick a value without importing genai. Vertex AI rejects `SafetyOff`; use `SafetyBlockNone` there.
- **Errors** live in `errors.go`. `APIResponseError` carries a `Reason` sentinel (`ErrBlocked` / `ErrEmptyResponse`) plus the `FinishReason`, and `Unwrap` returns the sentinel so `errors.Is` classifies it. Sentinel text is English with a package prefix (`gemini:` / `veo:` / `lyria:`) so a deeply wrapped error still names its origin; the human-facing context added by `fmt.Errorf` wrapping stays Japanese.
- **`genai.FinishReason` has two "unset" values.** Its Go zero value is `""`, but the SDK constant `FinishReasonUnspecified` is the string `"FINISH_REASON_UNSPECIFIED"`. Comparing only against the constant misclassifies responses that carry no finish reason as blocked. Always go through `isUnsetFinishReason` / `isBlockedFinishReason`. Candidate traversal is centralized in `firstCandidate`/`candidateParts` (extract.go) — the server can return nil candidate slots and nil parts, and per-extractor nil checks drifted apart once before.
- **`extractText` concatenates all non-`Thought` text parts.** Thinking-enabled models return the thought summary as a `Thought: true` part *before* the answer, and long answers can be split across parts — returning the first non-empty part gives you the wrong text. Thought parts are surfaced separately as `Response.Thoughts` via `extractThoughts`.
- **`GenerateOptions` uses pointers where zero is meaningful** (`Temperature`, `TopP`, `TopK`, `ThinkingBudget`) — `Temperature: 0` means deterministic, not unset. Use `new(expr)` (`new(float32(0))`). The `Ptr` helper this replaced was removed once a survey found no caller left in any of the ten downstream repos; `//go:fix inline` had already migrated them. `ThinkingConfig` is built by `buildThinkingConfig` and is only sent when something is actually specified, so the model's default thinking behavior isn't silently overridden. `ThinkingLevel` (model-independent tiers) and `ThinkingBudget` (token count) are alternative ways to say the same thing — when both are set, `ThinkingLevel` wins and the budget is dropped rather than sending a combination whose precedence is undefined. `ResponseJSONSchema` vs `ResponseSchema` follows the same rule.
- **Neither of those is deprecated**, despite appearances: the SDK's `GenerationConfig` (the batch/tuning payload type produced by `ToGenerationConfig`) marks its `ResponseSchema`/`ResponseMIMEType` `Deprecated: Use response_format instead`, but `GenerateContentConfig` — the type this package actually sends — has zero deprecation markers. Don't "fix" our usage based on the wrong struct.
- **`Config.HTTPClient` is the same field as the credentials, and `toClientConfig` exists to hide that.** genai skips ADC detection entirely when `ClientConfig.HTTPClient` is non-nil and then uses the given client as-is, so a plain `&http.Client{Timeout: ...}` sends no Authorization header and every Vertex call fails with 401 CREDENTIALS_MISSING — choosing a timeout silently gives up the auth. `toClientConfig` calls `UseDefaultCredentials` to reattach it, on a shallow copy so the caller's client is not mutated (that call rewrites `Transport`). The Gemini API backend is left alone: API keys travel as a header, not through the transport. `TestToClientConfigAttachesCredentialsToSuppliedHTTPClient` guards this; it needs real ADC and skips without it, which is why the bug reached production once already.

### veo package

- **The split between `gemini` and `veo` is "one round trip" vs "how to wait".** `gemini.StartVideo`/`PollVideo` own the genai client and do exactly one call each; `veo.Client` owns the polling interval, the overall timeout, and how many consecutive poll failures to absorb. Video generation is the only long-running-operation API here, so this is the only place that distinction exists. `veo` exposes both halves — `Submit` returns the operation name without waiting, `Wait` resumes from a name — so a caller splitting the two across job runs never has to reach past `veo` into `gemini.StartVideo`. `Generate` is the two together, and short-circuits when the submission response already came back `Done`. **`Wait` polls once immediately before starting the ticker** — the resume path usually finds the operation already finished, and waiting one interval first was pure dead time (`internal/poll`'s `TestRunPollsImmediately` pins this). That loop, along with the consecutive-failure tolerance and the deadline, is `internal/poll`'s; `veo` supplies `ErrPollFailed` as the sentinel to wrap when the failures stack up, so callers keep classifying them the same way. Logging goes through `veo.WithLogger` (default `slog.Default()`).
- **`PollVideo` deliberately opts out of retries via `noRetryHTTPOptions()`, while `StartVideo` keeps them.** Polling is already a retry loop; nesting the SDK's backoff (default 30s initial / 120s max here) inside it makes a single poll take tens of seconds and silently invalidates the caller's interval and timeout. Submission is the opposite case — a 429 there loses a whole video, so it must be retried. Don't "fix" the asymmetry.
- `veo` never imports genai. Its `Request`/`Reference`/`Media` are aliases of `gemini.VideoRequest`/`VideoReference`/`Attachment`, so there is no parallel type set to keep in sync, and `gemini.VideoGenerator` is two methods — tests use a fake with no SDK and no GCP credentials.
- **Input combinations are validated before sending** in `VideoRequest.buildSource`: Veo cannot combine `video` with `image`/`referenceImages`, and `lastFrame` is only valid alongside `image`. These are API-level facts, not policy — the *choice* of which mode to use belongs to the caller (`go-veo-orchestrator/ports.ClassifyVeoRequest` is where that decision lives for the MV pipeline).
- **`Request.ExtraBody` is the escape hatch for a missing *field*, not a missing *endpoint*** (it maps to `genai.HTTPOptions.ExtraBody`). It adds keys to the body of a call the SDK already makes, so it covers preview parameters on `generateContent`/`generateVideos` — and nothing else. When the SDK has no client for the endpoint at all (as of genai v1.71.0: the Interactions API behind `gemini-omni-flash-preview`), ExtraBody is useless and the choice is to wait for SDK support or write the call here. Nothing in ExtraBody is type-checked, so anything the SDK *does* model must use the real field.
- **ExtraBody cannot reach inside an array, and failing that quietly is destructive.** genai merges it with `recursiveMapMerge`, which recurses only when both sides are `map[string]any`; for any other type it overwrites. Vertex bodies are `{"instances": [...], "parameters": {...}}`, so `ExtraBody: {"instances": [...]}` replaces the whole array and takes the prompt and image inputs with it. `Request.ModifyRequestBody` (genai's `ExtrasRequestProvider`) receives the assembled body after that merge and is the only way to add a key inside `instances[0]`.
- Operation-level failure is reported on `VideoOperation.Failure` (wrapping `ErrVideoGenerationFailed`), not as the method's error: fetching the operation succeeded, so a transport error would misclassify it. genai exposes the failure as an untyped `map[string]any` (google.rpc.Status), so `videoOperationFailure` picks out code/status/message.

### lyria package

- `Workflow` is a facade over three roles: `Lyricist`/`Composer` (both implemented by `lyriaTextGenerator`) and `AudioGenerator` (`lyriaAudioGenerator`). Prompt construction is injected by the caller via `TextPromptGenerator` and `AudioPromptBuilder` — this library contains no prompt text.
- **There is deliberately no all-in-one `Run`.** One existed and no caller used it: ap-comp calls the three steps itself so it can gate between them (verify the composed recipe against the compose mode's declared structure and recompose with a shifted seed on failure, then measure and optionally review the audio). Those gates are per-product, so a bundled entry point only gets decomposed again at the call site. If a caller wants the straight-line sequence, it is `GenerateLyrics` → `Compose` → `GenerateAudio` in that order.
- `Compose` attaches `AIModels` and `Seed` to the recipe *after* generation — the recipe schema omits them on purpose so the model never invents them. `TestComposeAttachesModelsAndSeed` guards this; without it a seeded, reproducible run silently stops being reproducible.
- **`GenerateAudio` returns a `Track`, not bytes, because the response carries three things the caller cannot rebuild.** The bytes were all it returned, so the MIME type went back to being guessed from the content (WAV and MP3 get that wrong) and the model's text output was dropped on the floor entirely. Lyria returns the lyrics it actually performed there, so a caller can diff them against the lyrics it asked for and detect a dropped or repeated line mechanically instead of asking a reviewer model. `firstAudioAttachment` reads `Response.Attachments` rather than `Response.Audios` for the same reason — `Audios` is the same elements in the same order with the MIME type thrown away. Empty `SungLyrics` is normal (instrumental generation, or a model that returns no text), so it must not be treated as a failure; a response with *no audio attachment* is `ErrNoAudio`. `Track` is shared across singleflight callers, so `GenerateAudio` returns `Track.Clone()`.
- **Reading conversion is the prompt builder's job, and `WithReadingConverter` was removed rather than fixed.** It applied the converter to the whole assembled prompt, which for a Japanese recipe flattened Title, Theme and Lyric Narrative — context the model is told never to sing — into kana, losing the meaning and gaining no pronunciation. Only the code that assembled the prompt knows which lines are lyrics, so only it can scope the conversion; ap-music had already written that (per lyric line, section tags skipped) and documented the option as deliberately unused, which meant the library's branch ran `noopReadingConverter` in production and did nothing. The `ReadingConverter` interface went with it: this package never called it, and a one-method interface belongs to whoever calls it — keeping an uncalled one here would leave the same trap with the entry point filed off. The language gate went too, since `Recipe.IsJapanese` is exported and the builder was already applying it.
- Text generation (lyrics and recipe) shares one generic pipeline: `generateJSON[T]` in `text.go` (singleflight → Gemini call with JSON MIME type + `ResponseSchema` from `schemas.go` → `gemini.CleanJSONResponse` → unmarshal). The recipe schema deliberately omits `lyrics`/model fields — code attaches those after generation.
- **Singleflight + clone pattern**: identical concurrent requests are deduplicated via `callguard.Do`, which detaches from the caller's context (`context.WithoutCancel` + a per-run exec timeout, settable via `WithExecTimeout`, default 5m). Because results are shared across callers, every public method must return a **clone** (`music.Recipe.Clone`/`LyricsDraft.Clone`, `cloneBytes`) and must not write caller-specific data into the shared result. Hash framing for keys is unified in `callguard.WriteHashPart` (length-prefixed) — don't invent a second framing; `calculateImagesHash` stays local only because it hashes raw image bytes, which `callguard.Key`'s string parts would copy.
- Per-call model/mode/seed selection comes from the `AIModels` argument, falling back to the models set via `New(...)` options.
- **Everything that changes the output must be in the singleflight key.** `seed` in particular: it is passed to the generate call but is *not* implied by the prompt, so omitting it makes concurrent different-seed calls share one result. Use `callguard.SeedKey`. Both `generateJSON` and `GenerateAudio` do this.
- `AIModels` is embedded in `music.Recipe`, so its fields are flattened into recipe JSON — it carries explicit snake_case tags to match the rest of the struct. The struct definitions live in `music/` (moved in v1.17); `lyria`'s names are aliases. `music/music_test.go` pins the JSON wire format because downstream services persist recipes to GCS in this shape.
- Audio generation is rate-limited (`WithRateInterval`) and passes `Seed` through unconditionally (no backend-specific special-casing). Text and audio get **separate** `callguard.Guard`s — different models, different quotas, so congestion on one must not throttle the other.
- **The rate-limit wait happens outside the exec timeout** (`callguard.Do`). lyria used to call `limiter.Wait(execCtx)` inside the shared run, so a queued call could fail with `rate: Wait(n=1) would exceed context deadline` purely from congestion; `TestDoWaitsForRateIntervalOutsideExecTimeout` pins the fix.

## Conventions

- **Match the surrounding file.** `gemini/`, `veo/` and `callguard/` comment in Japanese; `lyria/` and `music/` comment in English. Wrap-context error messages follow the file; sentinel error text is always English with a package prefix (`gemini:` / `veo:` / `lyria:`).
- **No Markdown in Go comments.** godoc has no bold, so `**…**` reaches pkg.go.dev verbatim on every exported doc. The emphasis is already doing what the first sentence of a paragraph does — say it there and drop the markers. Markdown stays fine in `.md` files, this one included.
- The module targets Go 1.27: `errors.AsType`, `new(expr)`, and generic methods (`lyriaTextGenerator.generateJSON[T]`) are all in use.
- **`encoding/json/v2` is deliberately not adopted.** Every unmarshal in this module reads model output, which is exactly where v1's leniency is load-bearing: v2 matches member names case-sensitively, so a model that answers `"Title"` for a `json:"title"` field produces a zero-valued struct **and no error at all** — silent data loss, not a failure the caller can retry. v2 also rejects duplicate names and invalid UTF-8 that v1 accepts, which fights `CleanJSONResponse`'s whole purpose. Opting back out with `MatchCaseInsensitiveNames` / `AllowDuplicateNames` / `AllowInvalidUTF8` would leave nothing to gain: v1's error already names the failing path (`Recipe.sections.1.duration_seconds`), so `SemanticError.JSONPointer` only makes it machine-readable.
- **The README carries only what is expensive not to know.** Signatures, fields, defaults and the sentinel list belong in godoc, and reasoning belongs in this file; a section that restates an API is noise, and it stops being read at all once it reads like a reference. Adding a `Config` field or a sentinel is therefore a godoc edit, not a README edit — touch the README only when the *trap* changes. **The genai-kit / go-gemini-client comparison table lives in genai-kit's README and this one links to it** — genai-kit came second, so its readers are the ones asking how it differs, and a table in both places goes stale on one side (`public-docs/docs/library-readme-convention.md` §2.6). Sample code names concrete models; refresh them when the current generation moves on.
- **`callguard`'s exec timeout has no "unlimited", and the detach happens inside the shared closure.** The shared run is cut off from every caller's context (`context.WithoutCancel`), so the exec timeout is the only thing that can stop it — unlimited means one hung call holds a goroutine and blocks the same key forever. Detaching *outside* the closure instead lets the leader's `defer cancel()` kill the shared run when the leader returns early, taking every piggybacking caller with it.
- `CleanJSONResponse` is fuzzed (`FuzzCleanJSONResponse`, run for 60s in CI). Its invariant: if it changes the input at all, the result must be valid JSON — otherwise it leaves callers worse off than the raw string. **Extraction hands the input to a `json.Decoder` and stops where the first complete value ends** (`extractJSONValue`) rather than trimming the tail with a regexp or counting brackets: a decoder skips braces inside string literals, and the payloads here — lyrics, scripts, quoted source — routinely contain `}`, so a text-level trim cuts the body. This holds even with `ResponseSchema` set: a structured response can still arrive with a fence, an explanation, or a stray closer appended after a value that was already complete, which is past the point any API retry can fix. When repair fails the original string is returned unchanged, so the decode error the caller sees still points at the real breakage instead of a swallowed one.
- **Loop mechanics are tested once, in `internal/poll`** — immediate first attempt, interval, deadline over the in-flight call, consecutive-failure tolerance, caller-cancel vs. own timeout. What `gemini` and `veo` still test is what poll cannot know: that the right interval, timeout, tolerance and sentinel are wired in, and how a raw response maps to the package's own types. Re-testing the mechanics at a call site only buys two failures for one cause; deleting six such tests moved statement coverage by nothing, and five deliberate wiring mutations stayed caught.
- **The in-string repair is a single pass** (`escapeStringLiterals`): lone backslashes and raw control characters are fixed in one traversal. Splitting it in two makes the order load-bearing and easy to get wrong — escaping a raw newline *adds* a backslash, so a lone-backslash pass running afterwards doubles the escape it just wrote.
